# 예매 성능 테스트

JDK 25, Docker Compose, k6, curl이 필요합니다.

```sh
./benchmarks/run.sh
```

전용 DB(`55432`)와 API(`18080`) 준비 → 워밍업 500회 → 시나리오별 1,000회 요청 → DB 정합성 검증 → API·DB 종료까지 실행합니다. 매 시나리오 전에 전용 DB의 공연·예매 데이터를 초기화합니다. 이미 실행 중이던 전용 DB는 종료하지 않습니다.

| 시나리오 | 요청 분포 | 예상 성공 |
| --- | --- | ---: |
| low | 서로 다른 사용자·좌석 | 전체 요청 |
| hot | 사용자들이 인기 좌석 16개에 요청 | 최대 16건 |
| quota | 한 사용자가 서로 다른 회차·좌석에 요청 | 최대 4건 |

한 시나리오만 실행하거나 요청 수·동시 사용자를 바꿀 수 있습니다.

```sh
REQUESTS=3000 VUS=32 ./benchmarks/run.sh hot
```

터미널에 RPS·성공 RPS·p95/p99를 표시합니다. 결과 JSON과 API 로그는 `build/benchmark/<실행시각>/`에 저장합니다. 409 중 정책 거절만 정상으로 집계하며, 오류 응답·성공 수 불일치·DB 정합성 오류는 실행 실패로 처리합니다.

`scenarios.js`는 요청 분포, `reservations.js`는 HTTP 호출·측정을 담당합니다. `seed.sql`과 `verify.sql`은 데이터 준비·검증용입니다.

`hot`과 `quota`는 소진 후 거절이 대부분이므로 전체 RPS를 지속적인 선점 처리량으로 해석하지 않습니다. [전략별 측정 결과](../docs/decisions/001-reservation-concurrency.md)

## 반환 후 재선점

```sh
REQUESTS=120 VUS=16 WARMUP_REQUESTS=12 ./benchmarks/run.sh rehold
```

`rehold`는 별도로 실행합니다. `REQUESTS`와 `WARMUP_REQUESTS`는 HTTP 요청 수가 아닌 전체 시나리오 반복 수이며 각각 3 이상이어야 합니다. 반복마다 별도 좌석을 사용하고 다음 세 흐름을 순환합니다.

| 흐름 | 기대 결과 |
| --- | --- |
| 선점 → 취소 → 다른 사용자의 재선점·확정 | 기존 예매는 `CANCELLED`, 새 예매는 `CONFIRMED` |
| 선점 → 스케줄러 만료 → 다른 사용자의 재선점·확정 | 기존 예매는 `EXPIRED`, 새 예매는 `CONFIRMED` |
| 선점 → 확정 → 다른 사용자의 선점 시도 | 정책상 `409`로 거절되며 기존 예매가 좌석을 유지 |

실행 중 선점 시간을 5초로 설정하고 만료 스케줄러를 250ms 간격으로 실행합니다. 확정은 `benchmark` 프로필과 `reservation.benchmark.rehold-enabled` 설정을 함께 켠 로컬 API에서 호출합니다.
만료 시각부터 재선점 응답까지 걸린 시간은 만료 처리, 최대 100ms의 폴링 간격, 재선점 API 응답 시간을 포함합니다.
`verify-rehold.sql`은 예매 이력, 최종 좌석 소유자와 사용자별 구매 한도를 확인합니다.

## 폭주 부하에서 대기열 비교

`queue-baseline`은 선점 API로 직접 보내고, `queue`는 대기열을 통해 허가받은 요청만 선점 API로 보냅니다. 서로 다른 사용자와 좌석을 사용하므로 좌석 경합에 따른 거절을 부하 실패로 세지 않습니다.

```sh
REQUESTS=450 ARRIVAL_SECONDS=1 VUS=450 BENCH_DB_POOL_SIZE=2 HOLD_TIMEOUT_MS=500 ./benchmarks/run.sh queue-baseline
REQUESTS=450 ARRIVAL_SECONDS=1 VUS=450 BENCH_DB_POOL_SIZE=2 HOLD_TIMEOUT_MS=500 QUEUE_ADMISSIONS_PER_SECOND=60 QUEUE_MAX_IN_FLIGHT=8 ./benchmarks/run.sh queue
```

`REQUESTS / ARRIVAL_SECONDS`가 유입 목표 TPS입니다. 같은 DB 연결 수와 클라이언트 제한 시간을 유지하고, 대기열 없이 낮은 유입률부터 올려 오류·타임아웃이나 헬스 체크 실패가 나타나는 구간을 찾습니다. 그 유입률을 대기열을 켠 상태에서 다시 보냅니다. 예시의 DB 연결 수 2와 제한 시간 500ms는 실험 조건이며, 기본값은 각각 16과 1,000ms입니다.

- 유입 중 성공 TPS와 대기열이 소진될 때까지의 전체 성공 TPS를 각각 표시합니다. 두 수치 모두 클라이언트가 받은 HTTP 201을 셉니다. 클라이언트가 기다리다 포기한 요청도 DB에는 커밋될 수 있으므로 DB 검증에서 저장 건수를 별도로 확인합니다.
- 폭주 동안 헬스 체크를 보내고, 선점 오류·타임아웃, 대기열 만료·거절, 대기·선점·전체 응답의 p95를 구분합니다. 부하 종료 직후 프로세스 생존을 확인하고 앱을 정상 종료한 뒤 DB를 검증합니다.
- `VUS`는 대기 중인 사용자까지 수용할 만큼 설정합니다. k6 미전송이 발생하거나 실제 시작한 요청 수가 목표와 다르면 비교 실행이 실패합니다. 두 모드 모두 같은 방식으로 워밍업한 뒤 DB를 초기화합니다.
- `queue` 실행은 허가 없이 선점 API를 호출하면 429가 오는지 먼저 확인합니다. 이후 좌석 소유권과 구매 한도를 DB에서 검증합니다.

대기열은 기본 비활성입니다. 실험용 구현은 단일 서버의 메모리에 대기 상태를 저장합니다. 초당 허가 상한과 허가·사용 중인 자리의 동시 상한을 두며, 상태 조회나 등록 요청이 들어올 때 순번과 만료를 갱신합니다. 서버가 재시작되면 기존 대기표가 사라집니다.
`POST /reservation-queue`에 `userId`를 보내고 `GET /reservation-queue/{ticketId}`로 상태를 확인합니다. `ADMITTED` 상태가 되면 같은 사용자의 선점 요청에 `X-Queue-Ticket` 헤더를 보냅니다. 허가는 선점 요청 한 번에 사용되며, 처리 결과와 관계없이 동시 입장 자리가 반환됩니다.

2026-11-09 로컬 실험은 각 유입률을 1초간 적용했습니다. DB 연결 수는 2, 선점 요청 제한 시간은 500ms, 대기열의 허가 상한은 초당 60건과 동시 8건으로 설정했습니다. 대기열 없이 50·150·250 TPS에서는 타임아웃이 없었고, 측정한 지점 중 350 TPS에서 처음 타임아웃이 발생했습니다.

| 유입 TPS | 대기열 | 유입 중 성공 TPS | 전체 성공 TPS | 성공 응답 | 선점 타임아웃 | 선점 p95 | 대기 p95 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 350 | 미적용 | 103 | 49.2 | 103/350 | 247 | 500.2ms | — |
| 350 | 적용 | 27 | 27.2 | 350/350 | 0 | 40.2ms | 9.78초 |
| 450 | 미적용 | 197 | 97.3 | 198/450 | 252 | 500.1ms | — |
| 450 | 적용 | 25 | 25.1 | 450/450 | 0 | 48.4ms | 14.25초 |

네 실행 모두 프로세스가 살아 있었고 헬스 체크와 DB 정합성 검증을 통과했습니다. 대기열 미적용에서도 요청이 타임아웃된 뒤 예매가 저장돼, DB 저장 건수는 두 모드에서 각각 유입 건수와 같았습니다. 표의 성공 TPS는 클라이언트 응답으로 관측한 값이며, 각 조건을 한 번 실행한 로컬 표본입니다.
