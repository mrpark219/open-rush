# 예매 성능 테스트

JDK 25, Docker Compose, k6, curl이 필요합니다.

```sh
./benchmarks/run.sh
```

전용 DB(`55432`)와 API(`18080`) 준비 → 워밍업 500회 → 시나리오별 1,000회 요청 → DB 정합성 검증 → API·DB 종료까지 실행합니다. 매 시나리오 전에 전용 DB의 공연·예매 데이터를 초기화합니다. 이미 실행 중이던 전용 DB는 종료하지 않습니다.

| 시나리오 | 요청 분포                              | 예상 성공 |
|----------|----------------------------------------|----------:|
| low      | 서로 다른 사용자·좌석                  | 전체 요청 |
| hot      | 사용자들이 인기 좌석 16개에 요청       | 최대 16건 |
| quota    | 한 사용자가 서로 다른 회차·좌석에 요청 |  최대 4건 |

한 시나리오만 실행하거나 요청 수·동시 사용자를 바꿀 수 있습니다.

```sh
REQUESTS=3000 VUS=32 ./benchmarks/run.sh hot
```

터미널에 RPS·성공 RPS·p95/p99를 표시합니다. 결과 JSON과 API 로그는 `build/benchmark/<실행시각>/`에 저장합니다. 409 중 정책 거절만 정상으로 집계하며, 오류 응답·성공 수 불일치·DB 정합성 오류는 실행 실패로 처리합니다.

`scenarios.js`는 요청 분포, `reservations.js`는 HTTP 호출·측정을 담당합니다. `seed.sql`과 `verify.sql`은 데이터 준비·검증용입니다.

`hot`과 `quota`는 소진 후 거절이 대부분이므로 전체 RPS를 지속적인 선점 처리량으로 해석하지 않습니다. [전략별 측정 결과](../docs/decisions/001-reservation-concurrency.md)

## 반환 후 재선점

```sh
REQUESTS=120 VUS=16 WARMUP_REQUESTS=12 ./benchmarks/run.sh rehold
```

`rehold`는 별도로 실행합니다. `REQUESTS`와 `WARMUP_REQUESTS`는 HTTP 요청 수가 아닌 전체 시나리오 반복 수이며 각각 2 이상이어야 합니다. 반복마다 별도 좌석을 사용하고 다음 두 흐름을 순환합니다.

| 흐름                                                    | 기대 결과                                    |
|---------------------------------------------------------|----------------------------------------------|
| 선점 → 취소 → 다른 사용자의 재선점 → 선점 취소          | 두 예매 모두 `CANCELLED`                     |
| 선점 → 스케줄러 만료 → 다른 사용자의 재선점 → 선점 취소 | 기존 예매는 `EXPIRED`, 새 예매는 `CANCELLED` |

실행 중 선점 시간을 5초로 설정하고 만료 스케줄러를 250ms 간격으로 실행합니다. 일반 예약 생성과 선점 취소 API만 사용합니다. 재선점된 좌석의 중복 선점 거절도 확인한 뒤 선점을 취소합니다. 확정 좌석의 재선점 거절은 `ConfirmReservationTest` 통합 테스트에서 검증합니다.
만료 시각부터 재선점 응답까지 걸린 시간은 만료 처리, 최대 100ms의 폴링 간격, 재선점 API 응답 시간을 포함합니다.
`verify-rehold.sql`은 예매 이력, 최종 좌석 소유자와 사용자별 구매 한도를 확인합니다.

## 폭주 부하에서 대기열 비교

`queue-baseline`은 선점 API로 직접 보내고, `queue`는 대기열을 통해 허가받은 요청만 선점 API로 보냅니다. 서로 다른 사용자와 좌석을 사용하므로 좌석 경합에 따른 거절을 부하 실패로 세지 않습니다.

```sh
REQUESTS=450 ARRIVAL_SECONDS=1 VUS=450 BENCH_DB_POOL_SIZE=2 HOLD_TIMEOUT_MS=500 ./benchmarks/run.sh queue-baseline
REQUESTS=450 ARRIVAL_SECONDS=1 VUS=450 BENCH_DB_POOL_SIZE=2 HOLD_TIMEOUT_MS=500 QUEUE_ADMISSIONS_PER_SECOND=60 QUEUE_MAX_IN_FLIGHT=8 ./benchmarks/run.sh queue
```

`REQUESTS / ARRIVAL_SECONDS`가 유입 목표 TPS입니다. 같은 DB 연결 수와 클라이언트 제한 시간을 유지하고, 대기열 없이 낮은 유입률부터 올려 오류·타임아웃이나 헬스 체크 실패가 나타나는 구간을 찾습니다. 그 유입률을 대기열을 켠 상태에서 다시 보냅니다. 예시의 DB 연결 수 2와 제한 시간 500ms는 실험 조건이며, 기본값은 각각 16과 1,000ms입니다.

- 유입 중 성공 TPS와 대기열이 소진될 때까지의 전체 성공 TPS를 각각 표시합니다. 두 수치 모두 클라이언트가 받은 HTTP 201을 셉니다. 클라이언트가 기다리다 포기한 요청도 DB에는 커밋될 수 있으므로 DB 검증에서 저장 건수를 별도로 확인합니다.
- 폭주 동안 헬스 체크를 보내고, 선점 오류·타임아웃, 대기열 만료·거절, 대기·선점·전체 응답의 p95를 구분합니다. 부하 종료 직후 프로세스 생존을 확인하고 앱을 정상 종료한 뒤 DB를 검증합니다.
- `VUS`는 대기 중인 사용자까지 수용할 만큼 설정합니다. k6 미전송이 발생하거나 실제 시작한 요청 수가 목표와 다르면 비교 실행이 실패합니다. 두 모드 모두 같은 방식으로 워밍업한 뒤 DB를 초기화합니다.
- `queue` 실행은 허가 없이 선점 API를 호출하면 429가 오는지 먼저 확인합니다. 이후 좌석 소유권과 구매 한도를 DB에서 검증합니다.

대기열은 기본 비활성입니다. 현재 구현은 Redis에 대기 상태를 저장하며 같은 Redis 키를 사용하는 서버끼리 입장 제한을 공유합니다. 벤치마크 Compose는 개발 환경과 분리된 Redis(`56379`)를 실행하고, 실행마다 다른 대기열 키를 사용합니다. 등록·조회 요청과 주기 작업에서 입장과 만료를 처리합니다. 이 실행 스크립트는 여전히 단일 애플리케이션 기준이며 다중 서버 성능 측정은 후속 작업입니다.
`POST /reservation-queue`에 `userId`를 보내고 `GET /reservation-queue/{ticketId}`로 상태를 확인합니다. `ADMITTED` 상태가 되면 같은 사용자의 선점 요청에 `X-Queue-Ticket` 헤더를 보냅니다. 허가는 선점 요청 한 번에 사용되며, 처리 결과와 관계없이 동시 입장 자리가 반환됩니다.

아래는 Redis 전환 이전 메모리 대기열로 수행한 2026-11-09 로컬 실험 결과이며, 현재 Redis 구현의 성능 수치가 아닙니다. 각 유입률을 1초간 적용했습니다. DB 연결 수는 2, 선점 요청 제한 시간은 500ms, 대기열의 허가 상한은 초당 60건과 동시 8건으로 설정했습니다. 대기열 없이 50·150·250 TPS에서는 타임아웃이 없었고, 측정한 지점 중 350 TPS에서 처음 타임아웃이 발생했습니다.

| 유입 TPS | 대기열 | 유입 중 성공 TPS | 전체 성공 TPS | 성공 응답 | 선점 타임아웃 | 선점 p95 | 대기 p95 |
|---------:|--------|-----------------:|--------------:|----------:|--------------:|---------:|---------:|
|      350 | 미적용 |              103 |          49.2 |   103/350 |           247 |  500.2ms |        — |
|      350 | 적용   |               27 |          27.2 |   350/350 |             0 |   40.2ms |   9.78초 |
|      450 | 미적용 |              197 |          97.3 |   198/450 |           252 |  500.1ms |        — |
|      450 | 적용   |               25 |          25.1 |   450/450 |             0 |   48.4ms |  14.25초 |

네 실행 모두 프로세스가 살아 있었고 헬스 체크와 DB 정합성 검증을 통과했습니다. 대기열 미적용에서도 요청이 타임아웃된 뒤 예매가 저장돼, DB 저장 건수는 두 모드에서 각각 유입 건수와 같았습니다. 표의 성공 TPS는 클라이언트 응답으로 관측한 값이며, 각 조건을 한 번 실행한 로컬 표본입니다.

## Redis 대기열 다중 서버와 장애 테스트

Python 3, JDK 25, Docker Compose, k6가 필요합니다.

```sh
python3 benchmarks/run-distributed.py
```

`open-rush-distributed-benchmark` Compose 프로젝트의 전용 PostgreSQL·Redis와 호스트 JVM 1·2·4개를 사용합니다. DB 주소는 `55432`, Redis는 `56379`, 앱은 `18101`부터 `18104`입니다. 기존 단일 서버 벤치마크와 동시에 실행하지 마세요. 전용 DB의 업무 데이터는 각 부하 시나리오 전에 초기화하며 개발 DB에는 접근하지 않습니다.

전체 DB 연결 수 16개, 서버별 힙 256~512MB, 전역 동시 점유 32개, 입장 상한 초당 10,000개로 실행합니다. 입장 상한을 높여 고정된 입장 속도보다 애플리케이션과 DB의 처리 한계를 관찰하되 동시 점유 정책에 따른 제한은 남습니다. 기본 VU는 2,000개입니다. 각 서버 수에서 `100 × 서버 수`명/초로 30초간 워밍업해 서버당 목표 3,000개 흐름을 보내고, 기본 유입 100·300·600명/초를 각각 30초간 유지합니다. 워밍업에서도 미전송 여부를 기록하며 성능 기준 미달은 본 측정과 구분합니다. 워밍업 시간은 `--warmup-duration`으로 바꿀 수 있습니다.

k6는 등록과 예약 생성을 서로 다른 서버로 보내며, 조회는 예약을 생성할 서버로 보냅니다. 로드밸런서를 추가하지 않고 클라이언트가 순환 분배하므로 로드밸런서의 성능과 장애 처리는 측정하지 않습니다. 한 시나리오 반복은 HTTP 요청 하나가 아닌 대기열 등록부터 예약 생성까지의 사용자 흐름입니다. 서로 다른 사용자와 좌석을 사용하며 PG 호출은 포함하지 않습니다.

```sh
python3 benchmarks/run-distributed.py --instances 1,2 --rates 300,600 --duration 60 --skip-fault
python3 benchmarks/run-distributed.py --rates 600 --duration 60 --max-in-flight 128 --vus 2000 --skip-fault
python3 benchmarks/run-distributed.py --fault-only
```

실제 전송 수, 성공·실패율, k6 미전송, 유입 중 성공 TPS, 예약 생성 및 전체 흐름의 p95/p99, DB 연결 대기 샘플과 정합성을 기록합니다. 부하 단계의 기준은 오류율 0.1% 이하, 예약 생성 p95 500ms 미만, 전체 흐름 p95 1초 미만, 미전송 0건입니다. 기준을 넘은 경우에도 다음 부하 단계로 진행해 결과의 `k6ExitCode`와 각 threshold에 남기며, HTTP 성공 수와 DB 저장 수를 별도로 비교합니다. 기준 통과는 해당 실행의 관측 결과이며 운영 최대 용량 보장은 아닙니다.

장애 테스트는 서버 두 대에서 입장권을 소비한 예약을 DB 좌석 잠금으로 잠시 대기시킨 뒤, 전용 Redis만 중단하고 DB 잠금을 해제합니다. 예약 성공 응답 보존, 장애 중 신규 요청 거절, 기존 예약 조회와 멱등성 재전달, Redis 재시작 후 남은 대기표 및 만료 점유 회수를 확인합니다. 장애 중에는 동시성 40으로 등록 100건도 전송하며 일반 health와 liveness/readiness를 구분해서 기록합니다. 처리 점유 기한은 관찰을 위해 5초로 설정합니다. Redis는 AOF를 사용하며 이 테스트는 정상 종료 후 재시작 방식입니다. 강제 종료, 데이터 유실, 네트워크 지연, Sentinel 장애 전환은 별도 시나리오에서 다룹니다.

로그와 JSON은 `build/benchmark/distributed-<실행시각>/`에 저장합니다. 스크립트가 띄운 앱은 종료하고 새로 시작한 전용 컨테이너는 중지합니다. 기존에 실행 중이던 컨테이너는 유지합니다.

### 2026-11-22 Redis 측정 결과

애플리케이션 기준 커밋은 `4c53f22`입니다. 호스트는 논리 CPU 10개와 메모리 32GiB이며 Docker VM은 CPU 2개와 메모리 약 3.83GiB입니다. 앱과 k6는 같은 호스트에서 실행했습니다. PostgreSQL과 Redis는 같은 Docker VM을 공유합니다. JDK 25.0.2, k6 2.4.0, PostgreSQL 18, Redis 8.2.11을 사용했습니다. 서버별 CPU를 격리하지 않았으며 운영 용량이나 선형 확장률을 보장하는 실험은 아닙니다.

초기 30초 탐색에서 전역 동시 점유 32개, VU 500개로 100·300·600명/초를 비교했습니다. 100·300명/초는 서버 1·2·4대 모두 전송한 요청 전체가 성공하고 미전송이 없었습니다. 300명/초에서 서버별 9,000건을 처리했고 예약 생성 p95는 각각 16.0·59.4·23.2ms였습니다. 600명/초에서는 VU 부족과 대기 증가가 발생했으므로 실제 600명/초를 모두 보낸 실험으로 해석하지 않습니다.

전역 동시 점유를 128개, VU를 2,000개로 늘린 30초 탐색에서는 서버 1대가 18,000건을 모두 처리했습니다. 예약 생성 p95는 225.5ms, 전체 흐름 p95는 778ms였습니다. 하지만 아래의 60초 유지 시험에서는 재현되지 않아 이 단일 결과를 지속 가능한 최대 TPS로 채택하지 않았습니다.

다음은 전역 점유 128개, 전체 DB 연결 16개, VU 2,000개, 목표 600명/초를 60초간 유지한 결과입니다. 측정 전 `100 × 서버 수`명/초로 30초간 워밍업했습니다. 4대의 워밍업 자체에서도 미전송과 클라이언트 타임아웃이 발생해 이 조건에서 이미 부하를 감당하지 못했습니다.

| 서버 | 목표 흐름 | 실제 시작 / 성공 응답 | k6 미전송 | 유입 중 성공 TPS | 예약 생성 p95 | 전체 흐름 p95 | 기준 |
|-----:|----------:|---------------------:|----------:|-----------------:|--------------:|--------------:|------|
| 1대 | 36,000 | 24,470 / 24,470 | 11,530 | 374.5 | 492.8ms | 7,602ms | 미달 |
| 2대 | 36,000 | 36,000 / 36,000 | 0 | 599.5 | 206.0ms | 1,470ms | 전체 지연 미달 |
| 4대 | 36,000 | 20,037 / 20,037 | 15,963 | 300.6 | 617.9ms | 8,589ms | 미달 |

표의 본 측정에서는 시작한 요청이 모두 성공하고 DB 저장 수가 성공 응답 수와 일치했습니다. DB 정합성 검사도 모두 통과했습니다. 4대 워밍업에서는 성공 응답 8,085건에 비해 DB에는 8,185건이 저장되어, HTTP 요청 타임아웃 뒤에도 트랜잭션이 커밋될 수 있음을 확인했습니다. 부하 테스트의 신규 예약 요청에는 멱등성 키를 지정하지 않으며 자동 재시도하지 않습니다. 실제 클라이언트가 응답을 잃었을 때는 같은 멱등성 키로 결과를 복구해야 합니다.

높은 부하에서 DB 연결은 합산 16개가 모두 사용됐고, 1초 간격 샘플에서 연결 대기는 최대 합산 95~107개를 관측했습니다. 상태 폴링도 각각 약 60만·7만·69만 회 발생했습니다. 연결 대기와 폴링 증가를 확인했지만 이를 특정 단일 병목의 증명으로 보지는 않습니다. 공유 DB/Redis 자원, JVM 워밍업, 요청 분배, 폴링과 전역 점유 정책을 함께 분리해 추가 측정해야 합니다. 현재 결과에서는 서버 수만 늘려 처리량이 선형으로 늘어난다고 결론 내릴 수 없습니다.

## Sentinel 자동 장애 전환 검증

```sh
python3 benchmarks/run-sentinel.py
```

`docker-compose.sentinel.yml`로 Redis 3개(primary 1개와 replica 2개), Sentinel 3개(quorum 2), 앱 2개와 전용 PostgreSQL을 실행합니다. 앱도 같은 Docker 네트워크에 두어 Sentinel이 반환한 내부 Redis 호스트 이름에 접근합니다. 테스트마다 고유 Compose 프로젝트와 볼륨을 생성하며 끝나면 자신이 생성한 환경만 삭제합니다. `--keep`으로 환경을 남길 수 있습니다. API 주소는 `18201`, `18202`이며 기존 개발 환경과 별개입니다.

앱은 `redis-sentinel` 프로필로 연결합니다. 고정 primary 주소를 사용하지 않으며 대기열 읽기와 쓰기는 현재 primary로 보냅니다. Redis와 Sentinel의 실행 설정을 볼륨에 보관해 변경된 역할과 주소가 재시작 때 초기화되지 않게 합니다. Redis는 AOF와 `min-replicas-to-write=1`, Sentinel은 장애 판정 2초와 failover timeout 15초를 사용합니다. 로컬 검증용 설정이며 이 시간이 복구 시간의 상한은 아닙니다.

2026-11-22 실측 결과(`build/benchmark/sentinel-20261122-193403/results.json`):

| 조건 | 강제 종료한 primary | 승격 노드 | 승격 확인 | 두 앱의 기존 대기표 재사용 확인 | 결과 |
|------|--------------------|-----------|----------:|-------------------------------:|------|
| Sentinel 3대 정상 | `redis-1` | `redis-2` | 3.49초 | 7.48초 | 통과 |
| Sentinel 1대 중단, 2대 가동 | `redis-2` | `redis-3` | 3.60초 | 8.09초 | 통과 |

두 경우 모두 앱 컨테이너 시작 시각과 재시작 횟수가 유지됐습니다. 장애 관찰 중 HTTP 결과는 첫 번째 시나리오에서 200이 13건, 503이 69건이었고 두 번째에서 200이 15건, 503이 75건이었습니다. 503은 모두 `QUEUE_UNAVAILABLE`이었으며 500이나 클라이언트 연결 실패는 없었습니다. 이 관찰 구간은 대기표를 실제로 소비하기 전까지이며, 정상 소비 후 대기표 조회의 404와 구분했습니다.

승격 후 기존 대기표 2개씩으로 예약을 생성해 총 4건이 201을 반환했고 DB 정합성 검사를 통과했습니다. 새 등록도 승격된 primary에 저장됐습니다. 승격 전 해당 replica에는 Lua 캐시가 없었고 승격 후 `SCRIPT EXISTS=1`을 확인했습니다. 이전 primary를 재시작하면 `role=slave`, `master_link_status=up`으로 새 primary에 합류했고, `/data/redis.conf`의 `replicaof` 변경도 확인했습니다. 중단했던 Sentinel을 재시작한 뒤에는 세 Sentinel이 새 primary에 동의하고 quorum 검사도 통과했습니다. 기존 primary로 자동 failback하지 않습니다.

이 실험의 기존 대기표는 동일 Redis 연결의 `SET` barrier 후 `WAIT 2`로 두 replica에 복제된 것을 확인한 뒤 장애를 주입했습니다. 이는 검증 대상 데이터의 복제 여부를 통제한 것이며 애플리케이션의 모든 쓰기에 추가한 보장은 아닙니다. Sentinel은 비동기 복제이므로 최근 성공 응답을 받은 쓰기도 장애 전환 때 유실될 수 있습니다. 로컬 단일 Docker VM 구성은 프로세스 장애 전환의 검증이며 서버·가용 영역 장애에 대한 HA 검증은 아닙니다. [Redis Sentinel 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

기존 Gradle 테스트도 전체 169개가 통과했습니다. Sentinel 검증은 위 Python 실행으로 수행하는 별도 통합 시나리오입니다.

2026-11-23 파일 복구 후에도 두 시나리오를 재실행해 통과했습니다. 첫 전환은 `redis-1 → redis-3`으로 승격 3.44초, 앱 복구 7.44초였고, Sentinel 한 대를 중단한 두 번째 전환은 `redis-3 → redis-2`로 승격 3.57초, 앱 복구 8.13초였습니다. 앱 재시작 없이 기존 대기표로 예약 4건을 저장하고 이전 primary의 replica 복귀와 설정 저장을 다시 확인했습니다. 결과는 `build/benchmark/sentinel-20261123-213339/`에 있습니다.
